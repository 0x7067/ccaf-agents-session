The body of a request to the Claude API

model: the model we're going to use, e.g. claude-sonnet-4-6 or claude-opus-4-7
system: the system prompt. It defines the behavior the model will have and takes precedence over the messages array
messages: the whole conversation so far (user messages and assistant messages), sent every single time
tools: functions we expose to the model to extend its capabilities

Best practice: real tool descriptions run 3-4+ sentences (what it does, when to use it, limits). Compressed here to fit the slide.

{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "system": "You are a support agent…",
  "messages": [
    { "role": "user", "content": "Hi!" },
    { "role": "assistant", "content": "Hello!" },
    { "role": "user", "content": "Refund order #42" }
  ],
  "tools": [
    {
      "name": "get_weather",
      "description": "Fetches the current weather for a city",
      "input_schema": {
        "type": "object",
        "properties": { "city": { "type": "string" } },
        "required": ["city"]
      }
    },
    {
      "name": "process_refund",
      "description": "Refund an order on user request",
      "input_schema": {
        "type": "object",
        "properties": {
          "order_id": { "type": "string" },
          "amount": { "type": "number" }
        },
        "required": ["order_id", "amount"]
      }
    }
  ]
}

Foundations · 2 of 3

The API has amnesia

Every request is independent.
The model does not store state.
The whole conversation has to be included every time we communicate with the Claude API
// call 1
"messages": [
  {"role": "user", "content": "What's the capital of France?"}
]
// Claude replies: "Paris."

// call 2: resend EVERYTHING, then add the new question
"messages": [
  {"role": "user",      "content": "What's the capital of France?"},
  {"role": "assistant", "content": "Paris."},
  {"role": "user",      "content": "How many people live there?"}
]
// without the history, "there" means nothing to Claude
Analogy
Claude burns your messages after replying. Every reply resets its memory, so you send the entire conversation history alongside each new request. That is how it knows what you are talking about.

Agents · the whole secret

An agent = a model, using tools, in a loop

messages = [{ role: "user", content: task }]

while (true) {
  res = await claude.messages.create({ model, system, messages, tools })

  if (res.stop_reason === "tool_use") {
    toolCalls = res.content.filter(c => c.type === "tool_use")  // one or MANY

    toolResults = toolCalls.map(call => ({
      type: "tool_result",
      tool_use_id: call.id,
      content: runTool(call.name, call.input)   // your code!
    }))

    messages.push(
      { role: "assistant", content: res.content },
      { role: "user", content: toolResults }     // all results, one message
    )
    continue  // call Claude again, now with the results
  }

  if (res.stop_reason === "end_turn") {
    answer = res.content.find(c => c.type === "text").text
    break  // ✅ task complete: show the answer to the user
  }

  throw new Error("unexpected stop: " + res.stop_reason)  // max_tokens, …
}
The loop is dumb.
The model is smart.
The loop is ~25 lines of plain JavaScript anyone in this room can read. All the “magic” is the model choosing the next step.
The model decides when it's done, and that's what makes it an agent
A typical run: user request → tool_use → tool_use → end_turn
When a tool fails, you still send its tool_result, flagged with "is_error": true
Anti-patterns: parsing text for “task completed” · using max_iterations as the primary stop · “it produced text, so it must be done”
The only reliable completion signal: stop_reason === "end_turn"

Agents · one exam-critical distinction

Workflow vs. agent: who decides the steps?

Workflow

The code decides

Fixed pipeline: step 1 → step 2 → step 3. The model fills in blanks along a path you hard-coded. Predictable, cheap, great when the path is known.

Analogy
A recipe. It lists the exact steps in the exact order: chop, sauté, simmer for 20 minutes. Whoever cooks, even a brilliant chef, produces the same dish. Missing an ingredient? The recipe does not improvise. The cook executes; the recipe decides.
Back to the code
Your code calls the model at fixed points: summarize, then classify, then translate
The model fills in each blank, but it can never change the plan
A normal chat is the simplest case: you send a request, Claude returns one answer, done
Agent

The model decides

The model directs its own process: which tool, in what order, how many laps around the loop, and when it's done. For open-ended tasks where you can't script the path.

Analogy
A chef. You say "dinner for six, one vegetarian." The chef opens the fridge (tools), tastes and adjusts (tool results), goes back to the market if something is missing (another lap around the loop), and decides when the dish is ready to serve. Nobody hands the chef a list of steps.
Back to the code
The model picks which tool to call, in what order, and how many laps to take
Every tool result changes what it does next
It decides when the work is done, and signals it: stop_reason === "end_turn"

Agents · from one agent to many

The Task tool: how an agent spawns a subagent

// the coordinator's response: stop_reason "tool_use", like always
{
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_02…",
      "name": "Task",
      "input": {
        "subagent_type": "a11y-auditor",
        "description": "Audit UI accessibility",
        "prompt": "Audit the a11y of the app in src/. Return 4 findings."
      }
    }
  ],
  "stop_reason": "tool_use"
}
// follow-up: running this tool = starting a FRESH agent loop with
// that prompt. Its final answer comes back as the tool_result.
Nothing new to learn: Task is a tool like any other. Same tool_use block out, same tool_result back
Running it = starting a fresh agent loop: a subagent with its own messages array
subagent_type picks WHICH agent: one you defined up front with AgentDefinition
input.prompt is ALL the context the subagent receives
When that loop hits end_turn, its final text travels back to the coordinator as the tool_result
The raw API does not ship this tool: your harness defines it (named Task in the CCAF guide, Agent in newer SDK versions ↗). The model just calls it

Agents · the why before the how

Why subagents exist

context isolation
A subagent runs in its own fresh conversation. Its dozens of intermediate tool calls and file reads stay inside it; only the final report returns. The coordinator's context stays small, focused, and cheap.
in the demo: the a11y auditor reads the whole UI, the coordinator receives 4 lines
parallelization
Independent subtasks run at the same time. Three audits that take 2 minutes each finish in 2 minutes, not 6.
in the demo: all three auditors are spawned in one response and work concurrently
specialization
Each subagent carries its own tailored system prompt: deep expertise that would be useless noise in the main agent's instructions.
in the demo: the copy auditor knows i18n; the code auditor never hears about it
least privilege
Each subagent gets only the tools its job needs. A tool it was not given simply does not exist in its session: nothing to misuse, nothing to prompt for.
in the demo: all three auditors can read; none of them can write or run commands

Agents · multi-agent systems

Hub-and-spoke: a contractor and specialists

The coordinator decomposes the task, delegates via the Task/Agent tool, then merges results
Isolated context: a subagent knows only what's written in its prompt. It does NOT inherit the conversation
Each subagent returns one final report. If B needs what A found, the coordinator relays it
Analogy
A general contractor building a house: the plumber and the electrician each get their own work order and never call each other. Everything goes through the contractor, and that's why nothing gets lost.

The demo, in API terms: what to watch for

Spawning a subagent = the coordinator calling the Task tool (named Agent in newer SDK versions), a tool call like any other
The prompt passed to each subagent is its entire universe: context passing is explicit, or it doesn't happen. Click any spawn in the log to read it
Three spawns in one assistant response = the subagents run in parallel
Each report comes back as a tool_result, the same mechanism as any other tool
One more thing will be hiding in there: a hook.
The demo's permission callback hard-blocks every non-read tool. Not “please don't write files”: it cannot write files.
canUseTool: (name) =>
  READ_ONLY.includes(name)
    ? { behavior: "allow" }
    : { behavior: "deny", message: "read-only!" }
Prompts ask (>90%). Hooks enforce (100%). Money, legal, safety → hooks. Style and preferences → prompts.

          Return the top findings." \

-p / --print: non-interactive mode. Process the prompt, print, exit. The way to run Claude in CI
--output-format json + a schema → output a pipeline can parse (post PR comments automatically)
Fresh session for review. The session that wrote the code defends its own reasoning; a clean instance challenges it. Author ≠ reviewer.
Re-reviews: feed prior findings back in and ask only for new or unresolved issues, so there are no duplicate comments
Analogy
You don't grade your own homework. And the teacher keeps yesterday's margin notes so they don't write the same comment twice.

Recap

Seven sentences to take into the exam

The API is stateless: every call resends the full messages history.
Tool results travel back to Claude inside user messages, as tool_result blocks.
An agent is a model using tools in a loop; the model, not the code, decides the steps and when it's done.
The only reliable “done” is stop_reason === "end_turn". Never parse text, never rely on iteration caps.
Subagents have isolated context: they know only their prompt, return one report, and never talk to each other.
Hooks enforce deterministically; prompts only ask. Critical rules go in hooks.
In CI: claude -p + JSON output; review with a fresh session, not the author's.

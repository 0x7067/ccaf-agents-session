Foundations · 2 of 4

Two speakers. There is no “tool” role.

user — you (and, surprisingly, tool results)
assistant — the model (including its requests to use tools)
⚠ Coming from other APIs? There is no role:"tool" here. A tool's answer travels inside a user message, as a tool_result block.
Analogy
A walkie-talkie with two channels. When the model asks you to check the warehouse, you walk there, and you read the answer back into the radio. The warehouse never talks.

Foundations · 3 of 4

The API has amnesia

Each request is independent.
The model keeps zero state between calls.
“Continuing a conversation” = you resend the full history, plus one new message
That's why the messages array grows — and why context management matters
Once this clicks, the agent loop is obvious
// call 1
messages: [u1]                    → a1

// call 2 — resend EVERYTHING
messages: [u1, a1, u2]            → a2

// call 3 — again, everything
messages: [u1, a1, u2, a2, u3]    → a3
Analogy
Your pen-pal burns every letter after replying. If you want them to remember the story, your next letter must contain the whole story.

Agents · the whole secret

An agent = a model, using tools, in a loop

messages = [task]

while (true) {
  res = claude.create({ model, system,
                        messages, tools })

  if (res.stop_reason === "tool_use") {
    result = runTool(res.tool_call)   // your code!
    messages.push(res, asUser(result))
    continue                          // go around again
  }

  if (res.stop_reason === "end_turn") break   // ✅ done
}
The loop is dumb.
The model is smart.
The loop is ~10 lines anyone in this room can read. All the “magic” is the model choosing the next step.
The model decides when it's done — that's what makes it an agent
Anti-patterns: parsing text for “task completed” · using max_iterations as the primary stop · “it produced text, so it must be done”
The only reliable completion signal: stop_reason === "end_turn"
Agentschat = one lap around the loop · agent = as many laps as the task needs
Agents · one exam-critical distinction

Workflow vs. agent: who decides the steps?

Workflow

The code decides

Fixed pipeline: step 1 → step 2 → step 3. The model fills in blanks along a path you hard-coded. Predictable, cheap, great when the path is known.

Analogy
A recipe. Whoever cooks, the steps never change.
Agent

The model decides

The model directs its own process: which tool, in what order, how many laps around the loop, and when it's done. For open-ended tasks where you can't script the path.

Analogy
A chef. You name the dish; they open the fridge, taste, adjust, and decide when it's ready.
Agents“it loops” is not enough — a fixed pipeline can loop too. Agency = the model steers.
Agents · multi-agent systems

Hub-and-spoke: a contractor and specialists

The coordinator decomposes the task, delegates via the Task/Agent tool, then merges results
Isolated context: a subagent knows only what's written in its prompt — it does NOT inherit the conversation
Each subagent returns one final report. If B needs what A found, the coordinator relays it
Analogy
A general contractor building a house: the plumber and the electrician each get their own work order and never call each other. Everything goes through the contractor — that's why nothing gets lost.

Agents · debrief

What you just watched, in API terms

Spawning = the coordinator called the Task tool (named Agent in newer SDK versions) — a tool call like any other
The prompt you clicked on was the subagent's entire universe — context passing is explicit, or it doesn't happen
Three spawns in one assistant response = parallel execution
Each report came back as a tool_result — inside a user-role message, remember?
One more thing was hiding in there: a hook.
The demo's permission callback hard-blocks every non-read tool. Not “please don't write files” — it cannot write files.
canUseTool: (name) =>
  READ_ONLY.includes(name)
    ? { behavior: "allow" }
    : { behavior: "deny", message: "read-only!" }
Prompts ask (>90%). Hooks enforce (100%). Money, legal, safety → hooks. Style and preferences → prompts.

Claude Code in CI/CD

Same agent. Nobody at the keyboard.

# przsend already has CI (lint + typecheck).
# We add ONE job — the audit you just watched:

claude -p "Audit this repo: a11y, copy, code.
          Return the top findings." \
       --output-format json \
       --json-schema audit-schema.json
-p / --print — non-interactive: process the prompt, print, exit. The way to run Claude in CI
--output-format json + a schema → output a pipeline can parse (post PR comments automatically)
Fresh session for review. The session that wrote the code defends its own reasoning — a clean instance challenges it. Author ≠ reviewer.
Re-reviews: feed prior findings back in and ask only for new or unresolved issues — no duplicate comments
Analogy
You don't grade your own homework. And the teacher keeps yesterday's margin notes so they don't write the same comment twice.

Recap

Seven sentences to take into the exam

The API is stateless — every call resends the full messages history.
Two conversational roles; tool results are user messages with tool_result blocks — there is no tool role.
An agent is a model using tools in a loop; the model — not the code — decides the steps and when it's done.
The only reliable “done” is stop_reason === "end_turn" — never parse text, never rely on iteration caps.
Subagents have isolated context: they know only their prompt, return one report, and never talk to each other.
Hooks enforce deterministically; prompts only ask. Critical rules go in hooks.
In CI: claude -p + JSON output; review with a fresh session, not the author's.

Tool calling · 1 of 4

The call starts before the call

The client runs tools/list.
The model receives each tool's name, description, and input schema.
The model returns the chosen tool name plus JSON arguments.
The host passes those values to tools/call.
The important bitThe model does not execute the function. Your server does.
// what the model can see
{
  "name": "lookup-service",
  "description": "Look up one service...",
  "inputSchema": {
    "service": "string"
  }
}

// what the host calls
tools/call({
  name: "lookup-service",
  arguments: { service: "checkout-api" }
})
Tool calling · 2 of 4

The description is the router

ambiguous

"Gets service information"

Which identifier? What comes back? Should it search? When is another tool better?

The model has to guess.
discriminating

"Look up one service by exact catalog name"

Returns owner, tier, runbook, and health signals. Read the catalog resource first if the name is uncertain.

The boundary tells the model when not to call it.

Tool calling · 3 of 4

tool_choice decides who decides

auto

{"type":"auto"}

The model decides whether to call a tool at all, or just answer in text.

The default. What you want for a conversational agent.
any

{"type":"any"}

The model must call some tool. It still picks which one.

Use it when you need structured output and several schemas fit.
forced

{"type":"tool","name":"…"}

The model must call that exact tool.

Use it to guarantee a first step, such as extract_metadata before enrichment.
Exam instinctA good description makes the right tool likely. tool_choice makes a tool call certain. The host sets it on the API request; the MCP server never sees it.

Failure · 1 of 2

A useful error tells the model what to do next

dead end 
{
  "isError": true,
  "content": "Operation failed"
}

Retry? Fix input? Ask for access? Give up? The model cannot tell.

recoverable 
{
  "isError": true,
  "content": {
    "errorCategory": "validation",
    "isRetryable": true,
    "message": "Read the catalog and retry",
    "attemptedInput": { "service": "ghost-api" },
    "partialResults": null
  }
}
The model reads tool errors. The client handles protocol errors.11
Failure · 2 of 2

Zero results is not a broken search

successful empty result 
{
  "isError": false,
  "resultCount": 0,
  "matches": []
}

The search ran. There were no matches. Do not retry forever.

failed search 
{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false
}

The search never completed. The agent needs another route or human help.

What just happened?

The client launched the server and completed the initialize handshake.
Discovery returned plain schemas. That is the toolbox a model receives.
The resource gave us the map before we asked for one service.
tools/call returned ordinary content on success.
The failed call stayed inside the loop as readable isError: true content.
Nothing magical crossed the wire. Names, schemas, JSON arguments, and typed results did.The model adds judgment. MCP supplies the contract.
Architecture choices

Use the smallest server that solves the real gap

reuse

Standard integration?

Start with an existing maintained server. Jira does not become special because your agent calls it.

build

Unique team workflow?

Build a narrow server with clear permissions and descriptions.

remove

No longer useful?

Disconnect it. Every loaded tool definition consumes context and adds another choice.

Exam smellEighteen overlapping tools are not flexibility. They are a multiple-choice test you force the model to take on every turn.

Match the primitive to the job

tool

Let the model act

Use a tool with a discriminating description, narrow schema, and useful errors.

resource

Give the host a map

Use a resource for read-only context, catalogs, schemas, and documents.

Give people a starting point

Use a prompt for reusable workflows people choose from a menu or command.

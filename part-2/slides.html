The mental model · 1 of 3

MCP is like USB-C for tools

Without a shared protocol, each AI app needs its own adapter for each external system.
MCP standardizes how a client discovers a capability, calls it, and reads the result.
A server does not need model-specific code.
A client can connect to different servers without a new model integration for each one.
AnalogyAn MCP server is like a phone full of apps. The apps do the work; Claude chooses which one to use through the host.

Tool calling · 1 of 4

The call starts before the call

The MCP client sends tools/list.
The model receives each tool's name, description, and input schema.
The model returns the chosen tool name plus structured JSON input.
The host passes those values to tools/call.
AnalogySame as last session: the model asks, your code runs the tool. MCP puts that tool behind a server boundary so another host can use it too.
// what the model can see
{
  "name": "lookup-service",
"description": "Look up one service...",
  "inputSchema": {
    "type": "object",
    "properties": {
      "service": { "type": "string" }
    },
    "required": ["service"]
  }
}

// simplified JSON-RPC request; the SDK adds request metadata
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "lookup-service",
    "arguments": { "service": "checkout-api" }
  }
}
Tool calling · 2 of 4

The description is the router

ambiguous

"Gets service information"

Which identifier? What comes back? Should it search? When is another tool better?

The model has to guess.
It may call the wrong tool—or skip tools and guess.
specific

"Look up one service by exact catalog name"

Returns owner, tier, runbook, and health signals. Read the catalog resource first if the name is uncertain.

The boundary tells the model when not to call it.
AnalogyAn agent reaches for a built-in tool like Grep before an MCP tool that sounds the same. Name the data or context your server has that the built-in one cannot reach.

Tool calling · 3 of 4

What tool_choice controls

auto

{"type":"auto"}

The model decides whether to call a tool at all, or just answer in text.

The default for a conversational agent.
any

{"type":"any"}

The model must call some tool. It still picks which one.

Use it when you need structured output and several schemas fit.
forced

{"type":"tool","name":"..."}

The model must call that exact tool.

Use it when a particular tool must run first, such as extract_metadata before enrichment.
AnalogyA good description makes the right tool likely. tool_choice makes a tool call certain. The host sets it on the API request; the MCP server never sees it.
Tool calling · 4 of 4

Resources are the map. Tools are the hands.

resource

ravn://services/catalog

One read returns the service names, owners, tiers, and runbooks.

The host gets the catalog in one read instead of making exploratory calls.
tool

lookup-service

One call returns a specific record after the exact name is known.

It takes one exact name and returns one record.
AnalogyLast session, tools gave Claude hands. A resource gives it a map. If the model has to open every drawer to learn what exists, give it the map first.

Failure · 1 of 2

A useful error tells the model what to do next

dead end 
{
  "isError": true,
  "content": "Operation failed"
}

Last session's "refund unsuccessful" response leaves the model with no next step. Should it retry, fix the input, or ask for access? It cannot tell.

recoverable 
{
  "isError": true,
  "content": {
    "errorCategory": "validation",
    "isRetryable": true,
    "message": "Read the catalog and retry",
    "attemptedInput": { "service": "ghost-api" },
    "partialResults": null
  }
}

The model knows what failed and how to recover.

The model reads tool errors. The client handles protocol errors.12
Failure · 2 of 2

Zero results is not a broken search

successful empty result 
{
  "isError": false,
  "resultCount": 0,
  "matches": []
}

The search ran. Nothing matched. Do not retry.

failed search 
{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false
}

The search did not complete. Use another route or ask a human.

"No toilet paper" is an answer. "The door is locked" is not. Confuse them and the agent goes shopping instead of asking for a key.13

What just happened?

The client launched the server and completed the initialize handshake.
Discovery returned the names, descriptions, and schemas the model can use.
The resource gave us the catalog before we asked for one service.
The successful tools/call returned the service record.
The failed call returned isError: true with a recovery message, so the loop could continue.
The wire carried names, schemas, JSON arguments, and results.The model supplied judgment. MCP supplied the contract.
Architecture choices

Use the smallest server that solves the real gap

reuse

Standard integration?

Start with an existing maintained server. Jira does not become special because your agent calls it.

build

Unique team workflow?

Build a narrow server for the team-specific gap, with clear permissions and descriptions.

remove

No longer useful?

Disconnect it. Every loaded tool definition consumes context and adds another choice.

AnalogyEighteen overlapping tools turn every turn into a multiple-choice test. Add a tool when it gives the model access to something it cannot get another way.

The host owns the model loop and the MCP client.
Tools act. Resources inform. Prompts start workflows.
Tool descriptions decide routing. tool_choice decides whether a tool runs at all.
Project servers go in .mcp.json. Personal servers stay in ~/.claude.json.

Follow one order · Discovery

Before Claude can order, it reads the restaurant's capabilities

1The MCP client sends tools/list.
2The model receives each tool's name, description, and input schema.
3Claude writes the chosen tool name plus JSON arguments. That is the order ticket.
4The host passes those values to tools/call.

// what the model can see
{
  "name": "place-order",
  "description": "Order one exact menu item...",
  "inputSchema": {
    "type": "object",
    "properties": {
      "itemId": { "type": "string" },
      "quantity": { "type": "integer" }
    },
    "required": ["itemId", "quantity"]
  }
}

// JSON-RPC request — the SDK adds the envelope;
// "name" and "arguments" are the ticket Claude wrote
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "place-order",
    "arguments": { "itemId": "margherita-pizza", "quantity": 1 }
  }
}
Follow one order · Selection

The description gets the right ticket to the right station

ambiguous

"Orders food"

Which item identifier? How many? What comes back? Should Claude use it to browse?

The model has to guess.
It may call the wrong tool, or skip tools and guess.
specific

"Place one order by exact menu item ID"

Returns the order ID, accepted items, total, and ETA. Read restaurant://menu first if the item is uncertain.

The boundary tells the model when not to call it.
Restaurant model"Make food" sends everyone running. "One margherita pizza, quantity one" reaches the pizza station with no guessing.

Follow one order · Recovery

When the kitchen rejects a ticket, say why and what to try

dead end 
{
  "isError": true,
  "content": "Order failed"
}

The model cannot tell whether to retry, choose another item, or ask for help.

recoverable 
{
  "isError": true,
  "content": {
    "errorCategory": "validation",
    "isRetryable": true,
    "message": "Unknown item. Read restaurant://menu and retry",
    "attemptedInput": { "itemId": "truffle-pizza" }
  }
}

The model knows what failed and how to recover.

Restaurant modelA good waiter never just says "no". They say why ("we're out of truffle") and what to try ("check the menu").
The model reads tool errors. The client handles protocol errors.
Follow one order · Empty versus failed

"No sushi" is an answer. "Menu unavailable" is a failure.

successful empty result 
{
  "isError": false,
  "resultCount": 0,
  "matches": []
}

The search ran. Nothing matched. Do not retry.

failed search 
{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false,
  "message": "Menu access denied. Ask the restaurant manager."
}

The search did not complete. Use another route or ask a human.

Restaurant model"We checked, and there's no sushi today" is the waiter answering. "The kitchen door is locked" means nobody could check at all.
Empty data means the operation completed. An error means it did not.

Exam aside · tool_choice

The host can let Claude choose, require a call, or name the tool

auto

{"type":"auto"}

Claude decides whether to call a tool or answer in text.

Think: "order only if the guest needs something." The normal flow.
any

{"type":"any"}

Claude must call one of the available tools. It still chooses which one.

Think: "send some valid kitchen ticket before replying."
named tool

{"type":"tool","name":"place-order"}

Claude must call that exact tool.

Think: "this step must place the order."
Keep the boundary clearDescriptions guide which tool fits. tool_choice controls whether a call is optional or required. The host sets it; the MCP server never sees it.
Architecture choices

Use the smallest server that solves the real gap

reuse

Standard integration?

Start with an existing maintained server. Examples: Linear, Slack, Jira

build

Unique team workflow?

Build a narrow server for the team-specific gap, with clear permissions and descriptions.

remove

No longer useful?

Disconnect it. Every loaded tool definition consumes context and adds another choice.

Restaurant modelA menu with eighteen names for the same pizza slows every order. Add a tool when it gives the model a capability it cannot get another way.

Plan lunch. Use a prompt for a reusable workflow a person chooses.

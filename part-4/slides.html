The support agent · 3 of 9 · step 1 · Domain 5, section 1.4

Be careful with the system prompt of your customer support agent

The failure the exam describes

A guest writes "I was billed twice, my discount didn't apply, and I want to cancel." Single issues take your agent 3 to 4 tool calls, 91% success. This one takes 12+ calls, 54% success: the agent works the issues one at a time and fetches the same customer data for each.

one issue at a time · 7 trips around the loop
get_customer→lookup_order→process_refund→get_customer again→lookup_order→escalate_to_human→reply
Why does Claude fetch the customer twice?
Be careful with the system prompt. It steers every tool call. A safe-sounding line like "always verify the customer" makes Claude call get_customer when it does not need to, or again after every turn. The guide as an exam item.
Passing the history is not enough. Your loop already sends the whole conversation, so Claude does see the ID from two turns ago. But seeing a result is not being told to reuse it. Each turn Claude picks the next tool fresh, and the system prompt outranks the messages: "always verify" beats the ID already there.
Be careful when one message holds two issues. If the prompt , Claude works them one at a time, and each issue starts over: verify again, look up again. Every extra call sends the whole conversation to the API one more time, so time and cost grow with each one.
predictNow a different two-issue message: a guest asks for a refund on order #1234 and a shipping address change on order #5678. Claude gets single-issue messages right 94% of the time. On messages like this one it drops to 58%: it often solves only one of the two, or puts order #1234's details into the tool call for order #5678. Will this be fixed by the prompt lines on the right side of this slide?
No. Here Claude is not doing extra work, it is doing the wrong work. It has never seen a two-issue message handled well, so give it 2 to 4 few-shot examples that show one. Rule of thumb for the exam: extra calls and refetching mean no plan, so add the plan lines. Mixed-up parameters mean no pattern, so show examples.
The fix: four lines in the system prompt
1"Before you call any tool, list every distinct issue in the message." Now Claude plans once instead of starting over for each issue.
2"Verify the customer once. Reuse the customer_id and order facts already in the conversation." This replaces "always verify". The second issue uses CUST-2048 from the history instead of fetching it again. The exam calls this shared customer context.
3"When two tools do not depend on each other, request both in the same turn." Claude can return in one response. Your loop runs both and hands back both results together, so two trips become one.
4"Answer once, covering every issue you listed." One reply closes both issues. Nothing gets forgotten.
with the plan · 4 trips
issues: refund · price match→get_customer once→lookup_order→process_refund + escalate_to_human same turn→one reply
Nothing changes in your code. The loop from Part 1 already runs every tool_use block in a response and returns every result together. The whole fix is these four lines, plus .

The support agent · 4 of 9 · steps 2 and 3 · Domain 5, section 1.4

Be careful: a prompt cannot force the order of tool calls. Code can.

The failure the exam describes

Your prompt says to verify the customer first. Still, production logs show that in 12% of cases the agent skips get_customer and calls lookup_order using only the name the guest typed. Some refunds go to the wrong account.

the prompt says "verify first" · what happens 12% of the time
guest: "I am Mara Singh, refund ORD-1042"→lookup_order by name→process_refund→wrong Mara Singh gets $18.00
Why does the prompt not hold?
Be careful: a prompt is a request, not a rule. Each turn Claude picks the next tool from the whole context. Most of the time it obeys "verify first". Then a guest hands over a name and an order number in one line, the lookup looks ready to go, and the verify step gets skipped. Nothing stops it.
Be careful with louder wording. "Verification is MANDATORY before any order operation" is a wrong answer on the exam. It is still a request, and you just saw on the last slide what "always verify" does to the rest of the conversation.
Be careful with few-shot examples here too. Examples teach a pattern. They do not block a call. When money moves, "usually" is not good enough. The guide's words: for identity before financial operations, "prompts alone are insufficient".
predictA related trap. get_customer returns every match for a name. Two Mara Singhs. Today Claude picks the one with the most recent order, and 15% of the time that is the wrong account. Fix in code, or in the prompt?
Neither guesses. Tell Claude to (email, phone, order number) before any customer-specific action. The guest knows who they are; a ranking rule is still a guess. Chapter 9.1 lists "multiple matches" with one action: ask, do not guess.
The fix: a precondition in code, checked before every tool call
// runs in your loop before any tool executes (a PreToolUse hook in the SDK)
if ((tool === 'lookup_order' || tool === 'process_refund') && !state.verifiedCustomerId) {
  return { allowed: false, reason: 'No verified customer yet. Call get_customer first, then retry with the customer_id it returns.' };
}
// when get_customer returns exactly one match: state.verifiedCustomerId = result.customer_id;
Why this fix worksCode is deterministic: same input, same result, every time. A prompt rule is not. Claude does its best to follow it, but a rule can only ask, and 12% of the time something else in the message wins. This check runs in your code before every tool call, and it never has a bad day. So the order lookup and the refund always run for the right customer. The exam uses the same logic for any rule that must always hold, like a refund above a threshold: put it in code or a hook, not in the prompt.
with the lock · the same 12% case
lookup_order by name→DENIED · reason returned→get_customer → CUST-2048→lookup_order→process_refund right account

The support agent · 5 of 9 · step 5 · Chapter 9.1

Escalate on situations, not on moods

The failure the exam describes

Your agent resolves 55% of cases on first contact, against an 80% target. The logs show it escalates simple cases, like a standard replacement for damaged goods with photo proof, and tries to handle policy exceptions on its own. It has the line in the wrong place.

Why is the line in the wrong place?
Be careful with "escalate when it makes sense". That is not a line, it is a feeling. With no list of situations, Claude decides case by case, and it gets it backwards: the easy case looks scary, the policy exception looks like a puzzle it can solve.
Be careful with the three shortcuts everyone reaches for. Each one is a wrong answer on the exam. The guide's own table:
looks like a triggerwhy it fails
The customer sounds angry (sentiment analysis)Mood does not track how hard the case is. An angry guest may have a trivial case.
The model rates its own confidence 1 to 10The model can be confidently wrong. The number is not calibrated.
A separate classifier decidesOver-engineering. Needs training data you do not have.
predictThe agent has called get_customer and lookup_order and has every fact the system holds, but is still unsure. Which case should it escalate? (a) A guest wants to cancel an order shipped yesterday, arriving tomorrow. (b) A guest says the order never arrived, but tracking shows it delivered and signed for at their address. (c) A guest asks for competitor price matching; policy covers price drops on your own site and says nothing about competitors. (d) A message holds both a billing question and a return.
(c). That is a real policy gap, and the agent must not invent policy. The others are not gaps: (a) and (b) are cases the policy already answers, even if the answer is unwelcome, and (d) is two issues in one message, which slide 5 handles without a person.
The fix: the guide's escalation table, written into the system prompt
situationaction
The customer explicitly asks, "get me a manager"Escalate immediately. Do not try to solve it first.
Policy does not cover the request (competitor price matching when policy is silent)Escalate. The agent must not invent policy.
The agent cannot make progressEscalate after a reasonable number of attempts.
A financial operation above a thresholdEscalate, preferably enforced in a hook, not a prompt (slide 6).
Several customers match one nameAsk for another identifier. Do not guess (slide 6).
How to use it. Put these five rows in the system prompt as explicit criteria, then add 2 to 4 short examples of "escalate" and "resolve yourself". That is the exam's answer for the 55% agent: it draws the line where the line was missing. , in three short transcripts.

The support agent · 6 of 9 · step 5 · Chapter 9.3 and Domain 4.3

The manager never sees the transcript. Send a handoff that stands alone.

Why does the handoff come out thin?
Be careful with a one-line reason. The agent knows the whole case, so one line feels like enough. The manager knows nothing. Every fact left out becomes a question back to the guest, who already answered it once.
Be careful with free text. If the handoff is a paragraph the agent writes, some days it forgets the amount or the order ID. A prompt line saying "always include the amount" is a request again, and you know what requests do.
Be careful with fields the agent cannot know. If a field is required but the fact is missing, the agent fills it in. A made-up refund amount in a handoff is worse than an empty one.
predictYou make the handoff a tool with a JSON schema. Which fields do you mark required, and which do you make nullable? Think about customer_id, refund_amount, escalation_reason, and recommended_action.
Required: customer_id, escalation_reason, recommended_action, issue_summary, actions_taken. The agent always has these once it has done the work. Nullable: refund_amount, and any fact the case may not contain, so the agent can say "unknown" instead of inventing a number. Domain 4.3: make fields nullable when the source may not hold the information, to avoid fabricating values.
the bad version · a thin handoff, and what the manager gets
escalate_to_human {reason: "customer wants a price match"}→who? which order? refunded already?→manager asks the guest again

Think of it this wayA ticket lands on your desk: "make the UI pretty." Which UI? Which page? Which of your three products? You spend the afternoon asking, or guessing. Now the ticket says: product, page, a screenshot, what was tried, what they want, and why it came to you. You start working. The handoff is that ticket. The thin one sends the manager back to the guest. The full one lets them decide now, and the schema makes sure the agent cannot leave a field out.

The support agent · 7 of 9 · step 3 · Domain 5.1 and Chapter 11

Summaries blur numbers. Keep the facts outside the summary.

the failure the exam describes · practice question 54
turn 3 · guest: "the 15% discount you offered"→turn 25 · history is summarized→"promotional pricing was discussed"→agent quotes the wrong amount
Why do the numbers blur?
Be careful with progressive summarization. Every request carries the whole history (slide 5), so past some size you compress the old turns into a summary. That keeps the story and kills the details: 15%, $18.00, and dates become "about", "roughly", "a few". The guide lists this as one of the three context-window problems.
Be careful with the fixes that only delay it. A higher summarization threshold, a bigger window, or a summary prompt that says "keep every number verbatim". The last one is a request again. All three are wrong answers on the exam.
Be careful with tool results too. lookup_order returns 40+ fields when the step needs five. The extra 35 fill the context with noise, and the summarizer blurs them along with everything else. before they enter the context.
predictA 40-minute cooking conversation reaches 78,000 tokens: allergies, recipe quantities, clarified terms, and small talk. You must cut tokens. (a) Summarize everything. (b) Keep only the last 20,000 tokens. (c) Pull allergies and quantities into a facts block, summarize the small talk, keep the recent turns word for word. (d) Store it all outside and search it on demand.
(c), the hybrid. Exact facts in a block, the story summarized, the recent turns kept as they are. (a) and (b) lose the allergies. (d) is overkill for one session. It becomes the right answer when the history spans months of sessions and the user asks "what did we conclude in March?", which no summary can answer.

The support agent · 8 of 9 · step 6 · Domain 4.4 and Chapter 6.5–6.6

Check the answer in code before it leaves. Retry with the exact error.

the failure the exam describes · a valid extraction that is wrong
invoice → extract→{total: 150, line_items: [75, 70]}→schema check ✓ valid JSON→75 + 70 = 145, not 150→wrong total reaches the ledger
Why does valid JSON still come out wrong?
Be careful with trusting the schema. tool_use with a JSON schema removes syntax errors: the JSON parses, required fields exist, enums hold. It does not know that 75 + 70 is not 150, or that the total landed in the wrong field. The guide's split: syntax errors versus semantic errors.
Be careful with "try again". A retry that says "do it better" gets you the same guess. A retry that lets the model re-check arithmetic, formats, and field placement.
Be careful with retrying what is not there. If the due date is not on the invoice, no retry will find it, and a required field pushes the model to invent one. Make the field nullable, accept null, and send it to a person if it matters.
predictTwo failed extractions. A: the total says $150 but the line items add up to $145. B: the invoice has no due date and the schema requires one. Which one does a retry fix?
A, not B. In A the model can re-check the arithmetic once it sees the error. In B the data is absent; retrying a required field the source cannot fill produces a made-up date. Make due_date nullable. The exam skill is literally "identify when retry will be ineffective".
The fix: a check in code after every extraction, and a retry that carries the error
const out = await extract(invoice);            // tool_use + schema: syntax guaranteed
const sum = out.line_items.reduce((a, i) => a + i.price, 0);
if (sum !== out.total) {                         // business rule the schema cannot see
  out = await extract(invoice, { previous: out,
    error: `total = ${out.total}, but sum(line_items) = ${sum}. Re-check the values.` });
}
1Let the model show its own conflict. Ask for stated_total and calculated_total, plus conflict_detected. When they differ, your code sees a flag instead of a silent wrong number.
2Then check the reply itself before the guest sees it. Correct billing answers still scored 15% lower on satisfaction because the explanation skipped the policy reason, the timeline, or the next step. A self-critique pass, draft then check against those criteria, fixes it.
Think of it this wayThe schema is a spell-checker: every word is a real word, so "the invoice totals $150" passes even when the lines add up to $145. Validation is the proofreader with a red pen: she circles the line, writes what is wrong in the margin, and hands it back. A note that only says "do better" gets the same draft back. And if the date is simply not on the page, no proofreader can find it; write "unknown" instead of guessing.

The support agent · 9 of 9 · step 6 at scale · Domain 5.5 and Chapter 9.4

Stratified random sampling: check a few from every group

the failure the exam describes · Chapter 9.4
overall accuracy: 97%→"good enough, automate it"→scanned receipts: 40% wrong→nobody looks for weeks
Why does 97% hide a 40% failure?
Be careful with one overall number. 97% is an average over every document type and every field. A type that is 3% of the volume can be 40% wrong and barely move the average. The guide's words: aggregate metrics mask poor performance on specific types or fields.
Be careful with checking only the doubtful ones. If people review only low-confidence outputs, the confident-and-wrong ones are never looked at. The guide asks for error rates measured in the high-confidence group too.
Be careful with the word "confidence". On slide 7, the model rating its own confidence 1 to 10 was not a trigger. Here, a confidence per field, calibrated on a labeled set, is a valid routing signal. Same word, two things. The labeled data is the difference.
predictOverall extraction accuracy is 97%. Is the system ready to run without review?
Not yet. Break accuracy down by document type and by field, and sample the high-confidence outputs at random. The exam sentence: "an aggregate 97% accuracy can hide 40% errors for a particular document type." Automate a group only when its own measured accuracy is stable.
What the overall number hides
group (stratum)share of volumeaccuracy
Supplier A invoices70%99%
Supplier B invoices27%95%
Scanned receipts3%60%

The fix: sample every group, then automate only the stable ones
1Split the outputs into groups. By document type and by field: Supplier A totals, Supplier B due dates, receipt vendors. Each group is a stratum.
2Every night, pull a random sample from every group and check it by hand. Including the high-confidence group. Track the error rate per group. A new failure pattern shows up here first.
3Automate a group only when its measured accuracy is stable. Route low confidence or an ambiguous source to a person. Set the thresholds on a labeled validation set, not by feel.
Think of it this wayA factory ships 10,000 parts a day at a 97% pass rate. Testing only the parts that look off misses the one machine that makes shiny parts with the wrong thread. So every shift you pull a handful from every machine, including the one that never seems to fail, and measure them.

Why split the day into four loads: fit the worst-case order

day 1 · 00:00tray every
Same six orders in both kitchens, arriving at 00:05, 04:30, 09:00, 13:45, 18:20, and 22:50. A tray goes in at every purple marker. The oven is drawn at its ceiling, 24 hours: most batches finish far sooner, but a promise has to hold at the ceiling. Orange is waiting for a tray, violet is in the oven, and the mark at the end compares each order's total time with the 30-hour promise.
worst case = wait for the next tray + 24h. So: window ≤ promise − 24h
Why is this a strategy at all?
Splitting buys exactly one thing: a shorter wait before the tray goes in. The price stays half. The 24-hour ceiling stays. A batch can hold up to 100,000 requests, so size is never the reason. The wait is the only part of the worst case that is yours to shrink.
When to use which

The back office · 2 of 5 · steps 1 and 2 · Domain 1.6 and least privilege

Split the menu so it covers every course

Cover the whole question. "Plan the menu" split into three vegetable markets comes back with perfect tomatoes and no fish, no wine. The buyers did their job. The split was wrong before anyone left.
No two buyers at one stall. The chef partitions the markets before delegating. Overlap doubles tokens without adding breadth.

Fixed or dynamic plan (Part 1): a repeatable job is a fixed pipeline; an open investigation adapts from what it finds. Neither excuses a plan that misses a course.

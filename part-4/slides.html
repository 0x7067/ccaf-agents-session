The question underneath both scenarios

Who decides the next step?

One context has a limit. One agent cannot hold every source, every tool result, and every decision forever.
Recall Part 1: the agent loop sends a request, receives a response, runs tools, and sends the history back.
This part adds the design around that loop: who gets a task, what they receive, and what comes back.
Today's ruleGive each helper a clear assignment, the facts it needs, and a small return form. Keep the editor or host responsible for the whole story.
research

How do we split a question?

Parallel work saves time only when the assignments are independent and cover the whole question.

support

How do we stop a wrong action?

Prompt guidance helps. Code must guard identity, money, and policy boundaries.

Research desk · decomposition

Choose a fixed plan or adapt as you learn

fixed Prompt chaining

Use this when the steps are known before the work starts. It is easier to test and repeat.

  • extract metadata
  • extract the data
  • validate
  • enrich and format

dynamic Adaptive decomposition

Use this when the next step depends on what the first step discovers.

  • map the source set
  • find an uncovered area
  • prioritize the gap
  • add a new assignment
Exam shortcut: predictable structure → fixed pipeline. Open-ended investigation → let intermediate results change the plan. Do not decompose a broad question into the first narrow slice you notice.

In the guide, the spawning tool is called Task. Current Agent SDK traces may call it Agent. The job is the same: spawn an isolated subagent.

Research desk · failure is information

Keep useful work. Name the gap.

What came backMeaningCoordinator's next move
0 resultsThe query ran and found nothing.Accept it as a valid finding.
timeoutThe source could not be reached.Retry, use another source, or keep a marked gap.
partial_failureSome work completed, some did not.Pass the failure type, query, partial results, alternatives, and impact.
A blank answer and a broken connection are not the same thing.
Bad: catch the timeout and return [] with status: success. The editor will believe music had no evidence.
Good: return structured error context. The editor can retry the query or write music · PARTIAL COVERAGE.
Desk note"The archive had no articles" is a result. "The archive door never opened" is a failure. The report must tell the reader which one happened.

Support counter · tool choice

Good labels help the host choose the drawer

get_customer

Find one guest by name, email, phone, or order number. Return a verified customer ID.

Not an order lookup.

lookup_order

Read one order by order ID and verified customer ID. Return status, total, items, and eligibility.

Requires identity first.

process_refund

Refund a specific amount for a verified order when the policy allows it.

Financial action, guarded in code.

escalate_to_human

Send a policy gap, explicit manager request, or unresolved case to the manager queue.

Does not mean "search failed".
When the wrong tool keeps winning: inspect descriptions first. Add input formats, examples, and boundaries before building a routing classifier or merging every tool into one.
Support counter · safety boundary

The prompt asks. The guard decides.

guidance System prompt

"Always call get_customer before order operations." This teaches the normal path, but Claude can still make a mistake.

probabilistic compliance

enforcement Programmatic precondition

The application checks the state before the tool runs. Without one verified customer ID, it refuses both lookup and refund.

// before executing a tool call
if (['lookup_order', 'process_refund'].includes(name)
    && !state.verifiedCustomerId) {
  return deny('verify customer first');
}
deterministic guarantee
Callback to Part 1A prompt is the handbook line. A PreToolUse hook or guard is the till lock. Use code for money, identity, legal, and safety rules.
Support counter · facts and handoff

Keep the case small, then hand over the unresolved part

=== CASE FACTS · always included ===
customer_id: CUST-2048
order_id: ORD-1042
duplicate_charge: $18.00 confirmed
refund: REF-771 · 3–5 business days
open_issue: competitor price match
The order ledger had 19 fields. The host kept five. The important facts stay outside conversation summaries.
=== MANAGER HANDOFF · self-contained ===
{
  "customer_id": "CUST-2048",
  "issue_summary": "duplicate refund done; price match needs policy",
  "order_id": "ORD-1042",
  "actions_taken": ["verified", "looked up", "refunded $18.00"],
  "recommended_action": "decide whether competitor matching is allowed",
  "escalation_reason": "policy is silent on competitor prices"
}
Two different outcomes: an empty business result means a valid search found nothing. A blocked or failed operation carries an error. A policy gap becomes a structured human handoff.

Practice · answer the failure, not the buzzword

Two quick checks

Pick the smallest change that fixes the observed failure.

The exam often gives you four plausible improvements. Start with the root cause and the required guarantee.

HintDo not add a classifier when a tool label is vague. Do not add a stronger prompt when money needs a code-level lock.

If you remember eight rules

Keep the editor in charge

Research

1. Use a fixed pipeline when the steps are known.

2. Adapt when discovery changes the next assignment.

3. Spawn independent work in parallel.

4. Pass context explicitly. Reporters do not inherit the editor's history.

5. Keep partial results and mark the gap.

Support

6. Clear tool descriptions come before extra routing machinery.

7. Prompts guide. Code guards identity, money, and policy boundaries.

8. Keep exact case facts and hand off unresolved policy questions with a complete summary.

Pocket versionThe coordinator or host owns the whole story. Every helper gets a small assignment. Every failure says what happened. Every dangerous action meets a code-level check.
Questions welcome. Start with the failure you want the system to recover from.
